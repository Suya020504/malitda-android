# 말잇다 AI 개발 명세와 인계

2026년 10월 7일. 기준 실행 코드는 `f00b722`, APK0.2.0-debug다. 기존 Whisper·Vosk는 구현돼 있고, 새 의미 판단 모델은 아직 연결하지 않았다. 이 문서는 추가 구현·시험할 항목을 정의한다.

## 목표와 현재 동작

10월 7일 전체 설계 보완은 [최신 모바일·시스템 인계](complete-mobile-design-handoff-20261007.md)를 기준으로 확인한다. 현재 음성 의미 검색의 입력에는 STT 원문과 기존 `ui.candidates`가 들어가므로 기존 M1 승인 교정 후보가 포함될 수 있다. 카드는 뜻 ID를 직접 선택하고 현재 CONFIRMED 상태를 재조회하므로 별칭 검색·재정렬을 거치지 않는다. 이 읽기 연결을 순수 STT 후보만 사용한 조건과 혼동하지 않는다.

AI의 목표는 같은 학생에게 등록·확인된 뜻 중에서 후보 순서를 개선하는 것이다. 발음 치료, 미등록 뜻 생성, 학생 승인 대체를 하지 않는다.

공식 중간심사 의견과 10월 2일 팀 계획은 고유 표현을 사용하는 지적장애·언어장애 동반 청소년을 첫 실증 후보로 제안했다. 모집된 대상이나 효과가 확정됐다는 뜻은 아니다. 협력기관에서 한 가지 일상 소통 장면을 정하고, 학생이 사용할 수 있는 사진·그림·물건 선택·몸짓 등의 확인과 거절 방법을 먼저 찾는다. 확인 방법을 아직 찾지 못한 사례는 지원 관찰로 기록하고 독립 사용 성공으로 세지 않는다.

검증할 가설은 “익숙하지 않은 상대에게 개인 표현의 뜻을 전달할 때, 같은 음성인식 결과에 개인 사전과 뜻 확인을 더하면 전달 성공과 되묻기·도움 수준이 나아지는가”다. AI 재정렬은 그 흐름에서 실제로 발생한 후보 선택의 어려움을 줄이는지 별도로 평가한다.

| 부분 | 현재 구현 | 추가 구현·시험 |
|---|---|---|
| 음성 입력 | 로컬 Whisper/Vosk, 늦은 콜백 보호 | 같은 조건의 입력 품질·실제 발화 비교 |
| 의미 검색 | 확인된 사전, NFC·공백 정리 후 완전일치 | 문장 끝 부호 등 입력 차이 분석. 유사검색은 별도 옵션 |
| 재정렬 | RuleMeaningCandidateRanker가 기존 순서 유지 | 로컬 어댑터 우선, 필요한 경우 온라인 옵션 별도 검토 |
| 상황 | 의미별 contextLabel 저장, 요청 context는 현재null | 학생이 선택/입력한 대화 상황을 언제·어떻게 요청에 넣을지 결정 |
| 응답 검증 | ID전체 순열·보류·실패·현재성 재검사 | 실제 어댑터 지연·취소·오류·버전 변화 통합 시험 |
| 학생 확인 | 선택·맞아요/다른 뜻·이번 승인 | 실제 학생의 이해·선호하는 확인/거절 방식 확인 |
| 소리 | 시스템 한국어TTS, 오프라인 음성 우선 | 오프라인 음성 강제 여부·비동기 실패·취소된 재생의 늦은 콜백 보완 |

문장부호를 보존하는 현재 별칭 정규화와 기존 STT 교정용 정규화는 같지 않다. 예를 들어 “바람”과 “바람.”의 미일치를 먼저 분석하고, 규칙 변경·별칭 추가·유사검색·언어모델의 효과를 한 실험에서 섞지 않는다. 원문은 보존한다.

## 입출력 계약

새 어댑터는 `domain/MeaningRanking.kt`의 `MeaningCandidateRanker`를 구현한다. 현재 DTO를 임의로 바꾸지 않는다. 아래 값은 가상 예시다.

```json
{
  "profileId": 1,
  "sessionId": 42,
  "rawText": "바람",
  "candidates": [
    {"id": 11, "version": 2, "displayText": "산책하고 싶어요", "contextLabel": "밖에 나가기", "matchedAlias": "바람"},
    {"id": 12, "version": 4, "displayText": "바람이 차가워요", "contextLabel": "날씨", "matchedAlias": "바람"}
  ],
  "context": null
}
```

```json
{"orderedMeaningIds": [12, 11], "abstain": false, "provider": "local-experiment"}
```

재정렬 응답(`abstain:false`)은 **입력 ID 전체의 순열**이어야 한다. 새 문장·새 ID·다른 학생의 ID·중복·누락은 결과 전체를 거절한다. 판단이 어렵다면 `abstain:true`를 반환한다. 이때 빈 ID 목록도 허용하며 앱은 응답 순서를 사용하지 않고 기존 후보 전체의 순서를 유지한다. UI가 상위 일부만 먼저 표시하더라도 나머지 후보를 없애지 않는다.

어댑터에는 DB수정·학생 변경·등록/승인·공유·TTS 권한이 없다. 요청의 profileId/sessionId/version은 앱의 검증용 값이며 실제 사람 식별정보가 아니다. 온라인 전송에 그대로 사용할 식별자로 간주하지 않는다.

## 후보 수와 실패 처리

| 조건 | 앱의 동작 |
|---|---|
| 후보0개 | AI 호출 없이 카드·다시 말하기·함께 등록 |
| 후보1개 | 그 뜻 확인 화면. 자동 승인하지 않음 |
| 후보2개 이상 | 어댑터 호출 가능. 현재 제한1500ms |
| null·예외·시간초과 | 원래 후보 전체를 원래 순서로 제시 |
| abstain | 원래 순서로 제시. 선택·거절은 학생이 함 |
| 없는·중복·누락 ID | 응답 전체 거절, 원래 순서 |
| 학생/세션/등록 버전 변경 | 오래된 결과 적용 중지, 선택·승인 해제 |
| 등록 삭제·비활성·미확인 변경 | 현재 사용할 수 있는 뜻을 다시 고름 |
| 승인 후 문장·그림·뜻·학생 변경 | 이전 승인을 전달에 사용하지 않음 |

`MeaningViewModel.resolveRecognition`은 현재성 검사를 담당한다. `MeaningOperationGuard`와 `MeaningApprovalSnapshot`을 우회하지 않는다. 1500ms는 현재 코드 제한이며, 실제 기기에서 목표 지연과 모델 크기를 측정하기 전 임의로 늘리지 않는다.

## Jev 온라인 옵션

팀의 Jev가 **TypeSafe Jev**를 뜻한다면 외부 API 방식이다. 공식 문서는 API키와 `systemone` 엔드포인트를 설명한다. 이를 온디바이스 모델로 표시하지 않는다. [공식 빠른 시작](https://docs.typesafe.ai/introduction/quickstart)

현재 앱에는 인터넷 권한을 추가하지 않았으며 이 옵션을 채택하지 않았다. 먼저 가상 데이터로 별도 실험한다. 실제 표현·뜻·상황·원음의 전송은 대상 서비스와 전송 범위를 정해 별도 승인해야 한다. APK나 Git에 키를 넣지 않는다. 필요하다면 키는 서버에서 보관하고 요청마다 임시 후보 ID를 만들어 로컬 ID와 매핑한다.

Choice 결과를 쓰더라도 선택 ID만 반환해 다른 후보를 버리면 현재 계약에 맞지 않는다. 유효한 선택 ID를 앞에 두고 나머지를 기존 순서로 이어 전체 순열을 만든다. 공급자의 confidence를 정확한 뜻의 확률로 취급하지 않으며, 임계값은 같은 조건의 비교 시험 후 결정한다.

## TTS와 전달의 추가 보완

현재 `TtsManager`는 오프라인 한국어 음성을 우선 선택하지만, 없을 때 Ready(offline=false)가 가능하다. 시스템 TTS서비스의 네트워크 사용은 앱의 인터넷 권한 유무만으로 단정할 수 없다. 또한 비동기 onError는 speaking/progress를 정리하고, 새 의미 화면에 명시적인 실패 이벤트를 전달하지 않는다.

릴리스 전에 앱 담당이 다음을 보완·확인한다.

1. Preview와ApprovedDelivery 목적을 구분하고 해당 학생·세션·등록 버전의 현재성을 확인한다.
2. 오프라인 한국어 음성이 없을 때 외부 음성으로 자동 전환할지 판단한다. 기본 권고는 문장·그림 유지와 기기 음성 설정 안내이며, 온라인 사용은 별도 동의 범위로 정한다.
3. 재생 요청마다 utteranceId와세션 토큰을 연결하고 Started/Completed/Failed/Cancelled를 구분한다. 취소·재선택 이후 늦은 콜백은 무시한다.
4. 실패하면 뜻의 그림·문장을 유지하고 재시도/화면으로 보여주기를 제공한다.
5. 큐 접수, 실제 소리 출력, 상대 이해, 실제 다른 앱 전송을 성공 지표 하나로 합치지 않는다.

## 담당 파일과 통합 경계

| 담당 | 소유할 변경 | 통합 담당과 맞출 변경 |
|---|---|---|
| AI 담당 | 별도 `ai/ranking/` 어댑터, 가상 사례·응답 변환·오류 시험 | 모델/의존성/모델 크기/온라인 옵션 |
| 앱 통합 담당 | MeaningViewModel·AppContainer·DB·승인·TTS·화면 | DI연결·설정·모델 준비/해제·콜백·사용자 상태 |
| 디자이너 | 모바일 인계 프레임·공통 컴포넌트·자산·문구 | 화면ID·새 상태·버튼 동작·등록 단계 분리 |

AI담당은 공유 VM과DB를 동시에 고치지 않고 어댑터를 PR로 넘긴다. 앱 담당이 같은 입력·사전·후보 조건에서 검증해 주입한다. 현재 `AppContainer`의 기본 규칙 구현은 어댑터 검증 전 유지한다.

## 시험과 출시 판단

`handoff/ai-contract-vectors-20261007.json`은 **가상 명세 벡터**이며 실행 완료 결과가 아니다. 기존 검증45+10은 현재 앱의 개발 검증이고, 추가 모델의 성능이 아니다.

규칙 기준 C와재정렬 조건 D는 같은 STT결과·사전 버전·후보 전체를 사용한다. 유사검색을 켜는 조건은 따로 비교한다. STT의 CER/WER와 의미 선택·거절·독립 과업 완료·도움 수준·오전송을 구분한다. 참여자 수와 목표 효과 수치는 자료가 없으므로 확정하지 않는다.

먼저 계약·예외·취소·학생 분리·오래된 응답을 가상 사례로 시험한다. 다음으로 같은 뜻 과업과 학생의 실제 확인 방법을 검증한다. 미승인 전송·학생 간 혼합·동의 없는 저장/전송·취소 후 전달이 남으면 릴리스를 중단한다. 실제 기기·당사자·정식 서명·전체 모바일 마감은 후속 확인이 필요하다.

기존 상세 타입과 취소 규칙은 [AI 연결 계약](ai-integration-contract.md), 구현 결과는 [0.2.0 검증 기록](verification-0.2.0.md)을 함께 확인한다. 공식 피드백·녹음 검토와 팀 계획의 보관 위치는 프로젝트 Wiki의 현재상태에 남겨 두었으며, 개인 원음·참가자 서류는 이 저장소에 포함하지 않는다.
