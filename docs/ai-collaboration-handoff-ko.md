# 말잇다 앱·AI·디자인 협업 안내

현재 앱에는 Whisper·Vosk를 이용한 기기 내 음성인식 AI가 들어 있다. 새로 연결할 의미 판단 기능은 사용자가 확인해 등록한 뜻 중에서 후보의 순서를 정하거나 판단을 보류하는 역할을 맡는다. 등록하지 않은 뜻을 만들거나 당사자 확인을 건너뛰지 않는다.

목표는 `음성 인식 → 개인 표현 검색 → 뜻 선택 → 학생 확인·승인 → 전달`을 하나의 앱에서 이어 주는 것이다. 이번에 추가한 연결 계약의 기본 구현은 규칙 방식이며, sLLM·Jev 어댑터는 아직 연결하지 않았다. 아래는 역할과 전달물을 맞추기 위한 안내이며 팀의 최종 역할·마감을 대신 확정하는 문서는 아니다.

## 누가 무엇을 맡는가

| 담당 | 맡을 일 | 넘길 결과물 | 함께 정해야 하는 변경 |
|---|---|---|---|
| 민태님 | 로컬 STT 준비·비교, 입력 품질 개선, 필요할 때 등록된 의미 후보의 선택적 재정렬 실험 | STT 변경 이유·같은 조건의 결과, `MeaningCandidateRanker`를 구현한 별도 어댑터, 가상 사례와 실패 처리 | 기본 STT 변경, 모델 추가, 온라인 API 도입, 앱 의존성 추가는 앱 담당과 검토 |
| 앱 개발: 연수·Codex | Room 사전 저장·검색, 사용자별 분리, 대화 상태, 학생 선택·승인, 확인·전달 화면, APK 제작·검증 | 후보 요청 생성과 응답 검증, 실패 시 기존 흐름, 테스트 결과와 검증 가능한 APK | DB 구조·등록 상태·승인 규칙·화면 적용은 앱 담당이 통합 |
| 서빈님 | 전달할 42개 화면의 ID 유지, 공통 색·글꼴·간격·버튼·후보 카드 스타일 리터칭 | 화면 ID 목록, 수정 화면·공통 스타일, 개발에 필요한 자산·치수, 기존 화면과의 대응표 | 새 화면·화면 ID 변경·동작 변경은 앱 담당과 먼저 맞춤 |

현재 저장소의 디자인 안내는 9월 21일 기준 `S01~S27` 화면과 `O_*` 확인·편집 상태를 설명한다. 다음 42개 화면 전달본은 그 자료와 대응을 확인해야 한다. 42개 화면을 현재 코드에 모두 구현한 상태로 해석하지 않는다. 디자인은 표현·상태를 보여 주고, 실제 저장·사용자 분리·승인·전달 동작은 앱 개발에서 연결한다.

## 기준선과 추가 실험

첫 기준선은 완전일치 검색이다. 예를 들어 같은 사용자에게 등록된 표현이 “바람”이면 정규화한 인식 결과가 “바람”과 같을 때 그 표현의 확인된 뜻을 제시한다. 후보가 여러 개면 기존 규칙 순서를 유지한다. 새 언어모델 없이도 개인 표현 등록·뜻 선택·확인·전달 흐름을 검증할 수 있다.

유사검색은 별도 옵션으로 비교한다. “바람”과 비슷한 입력을 어느 범위까지 연결할지, 오인식과 미등록 표현을 어떻게 거절할지 정해야 한다. 유사검색의 이득과 sLLM의 순위 조정 이득을 한 실험에서 섞지 않는다. 각각 같은 STT 결과와 같은 사전·후보를 사용한다.

작은 언어모델(sLLM)은 완전일치 기준선에서 반복되는 후보 선택 실패가 확인된 뒤 실험한다. AI는 이미 검색된 후보 전체의 순서만 바꾸거나 “판단 보류”를 반환한다. 학생이 뜻을 선택하고 확인하는 절차는 모든 조건에서 유지한다.

Jev는 팀 계획서의 조건부 검토 항목이다. TypeSafe Jev를 뜻한다면 외부 API를 사용하는 온라인 단계로 보며, 도입 승인·전송할 자료·키 관리·실패 복구·같은 조건의 효과 비교를 먼저 결정한다. 현재 계약은 Jev를 채택하거나 인터넷 권한을 추가하지 않는다.

## AI에 넘기는 내용

앱은 같은 사용자에게 등록·확인된 후보만 만든다. AI에는 인식된 표현, 후보의 번호·버전·등록 문장·상황, 이번 대화의 상황을 준다. 후보 번호는 문장을 바꾸지 않고 순서만 돌려받기 위한 값이다. 다음 숫자와 문장은 가상 예시다.

```json
{
  "profileId": 7,
  "sessionId": 42,
  "rawText": "바람",
  "candidates": [
    {
      "id": 11,
      "version": 1,
      "displayText": "산책하고 싶어요",
      "contextLabel": "밖에 나가기",
      "matchedAlias": "바람"
    },
    {
      "id": 12,
      "version": 3,
      "displayText": "바람이 불어요",
      "contextLabel": "날씨",
      "matchedAlias": "바람"
    }
  ],
  "context": "날씨를 이야기하는 중"
}
```

`rawText`는 STT가 인식한 표현이고 `displayText`는 등록해 확인한 뜻이다. 화면과 데이터에서 두 내용을 구분한다. `profileId`·`sessionId`·`version`은 다른 사용자의 결과나 오래된 대화·수정 전 등록 내용을 적용하지 않도록 앱이 확인할 값이다.

규칙 기본 결과는 `orderedMeaningIds: [11, 12]`, `provider: "rules"`다. 선택적 AI 실험이 상황을 보고 두 번째 후보를 앞에 두려면 다음처럼 ID만 반환한다. 이 JSON은 기기 내 타입을 설명한 예시이며 외부 API 주소·요청 형식은 아니다.

```json
{
  "orderedMeaningIds": [12, 11],
  "abstain": false,
  "provider": "local-experiment"
}
```

이 응답의 뜻은 “12번 후보를 먼저 보여 주자”다. 12번 뜻을 학생이 선택·승인했다는 의미는 아니다. 판단이 어려우면 같은 결과 타입에서 `abstain: true`와 빈 ID 목록을 반환할 수 있다. 앱은 모든 원래 후보를 원래 순서로 유지하고 학생이 선택하도록 한다.

등록된 후보 밖의 번호, 중복·누락된 번호, 오류·1,500ms 시간초과는 원래 후보 순서로 돌아간다. 앱은 응답 직전 사용자·대화·등록 버전도 확인한다. 번호가 유효해도 다른 대화로 바뀌었거나 등록 내용이 수정됐으면 늦은 결과를 버린다.

실제 사람의 식별정보와 원음은 AI 요청에 넣지 않는다. 개인 표현·뜻·상황도 외부로 전송하지 않는다. 온라인 실험을 별도 승인하더라도 앱 내부 ID를 그대로 보내지 않고 허용된 가상·비식별 사례와 임시 번호부터 사용한다. API 키를 APK·앱 자산·Git에 넣지 않는다.

개발용 정확한 타입과 실패 처리 예시는 [AI 연결 계약](ai-integration-contract.md)과 `domain/MeaningRanking.kt`에 있다. 민태님은 별도 어댑터에서 이 계약을 구현하고, 앱 담당이 요청 생성·응답 적용·오래된 결과 거절을 연결한다.

## 언제 무엇을 넘길 것인가

“다음 주 내 디자인 전달”은 2026년 10월 5일~10월 11일 범위다. 10월 9일은 중간 확인을 위한 권고 시점이며 합의된 마감일이 아니다. 정확한 전달일과 가능한 범위는 팀에서 확정한다.

| 전달 순서 | 준비할 내용 | 확인할 것 |
|---|---|---|
| 디자인 전달 전 | 42개 화면 ID와 기존 화면 대응, 공통 스타일, 등록·선택·다른 뜻·취소·오류 상태 | 앱 담당이 화면 동작과 ID를 해석할 수 있는가 |
| AI 연결 전 | 가상 기준 사례 약 20~30개를 준비하는 안 | 제안 규모이며 실제 참여자 수·검증 완료 사례 수가 아님 |
| 연결 시 | 동일한 입력·사전·후보로 규칙과 선택적 재정렬 비교 | 없는 ID·누락·보류·시간초과·사용자 전환·등록 수정 처리 |
| APK 확인 시 | 등록부터 학생 선택·확인·전달까지 실행 | 원문·의미 분리, 사용자 간 데이터 분리, 승인 전 전달 차단, 오프라인 복구 |

가상 사례에는 뜻이 하나인 표현, 여러 뜻의 “바람”, 미등록 표현, 잘못된 인식, 후보 없음, 다른 뜻·취소를 포함한다. 약 20~30개는 초기 개발 점검을 위한 제안이다. 가상 사례 통과를 실제 사용자의 의사소통 개선으로 보고하지 않는다. 당사자의 효과는 별도 동의·참여 조건과 같은 과업 비교를 통해 확인해야 한다.

## 코드를 합칠 때

개별 브랜치에서 소유 파일을 수정하고 PR로 검토한다. `main`에 여러 사람이 동시에 직접 커밋하지 않는다. AI 담당은 어댑터와 AI 테스트를, 앱 담당은 데이터·상태·승인·화면·주입을, 디자인 담당은 화면·스타일·자산 전달본을 맡는다. 공통 파일 변경이 필요하면 먼저 수정 범위를 맞춘다.

합치는 담당자는 모든 후보를 보존하는지, 새 뜻을 생성하지 않는지, 오류·늦은 결과에서도 학생 선택·승인이 유지되는지 확인한 후 반영한다. 코드 기준은 `codex/personal-meaning-mvp` 브랜치이며 이번 앱의 실행 결과와 남은 확인은 [0.2.0 검증 기록](verification-0.2.0.md)에 있다.
